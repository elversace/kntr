# إعداد KNTR على Railway

هذا الدليل لتشغيل خادم اختبار مع PostgreSQL. أُعدّت ملفات المصدر للتشغيل، لكن محاولة إنشاء مشروع Railway توقفت بسبب حد الموارد في الخطة المجانية (`resourceProvisionLimitExceeded`). لم تُنشر خدمة أو قاعدة بيانات جديدة، ولم يُولّد نطاق HTTPS لهذه النسخة بعد.

## 1. المصدر وبيئة الاختبار

استخدم مستودع GitHub خاصًا تحت حساب `elversace` يحتوي على الحزمة كاملة. عند ربط المستودع بخدمة التطبيق في Railway، اجعل **Root Directory**:

```text
kntr-package/kntr-backend
```

أنشئ بيئة اختبار منفصلة وخدمة PostgreSQL داخل المشروع نفسه. إذا رفض الحساب توفير الموارد، يلزم معالجة حد الخطة أو إتاحة الموارد من حساب Railway قبل إكمال النشر. لا تُرسل رموز GitHub أو Railway أو كلمات المرور في المحادثة؛ أدخل الأسرار داخل إعدادات الحساب والخدمات الخاصة.

## 2. البناء وتشغيل الخدمة

اضبط القيم الآتية من **إعدادات خدمة التطبيق في Railway**. ملف `deployment/railway-plan.json` في جذر الحزمة يوثّق خطة الإعداد للمراجعة؛ لا ينفّذه Railway تلقائيًا. الخدمات الجديدة تستخدم إعدادات الخدمة، ولا تعتمد هذه الحزمة على `railway.json` أو `railway.toml`:

| الإعداد | القيمة |
|---|---|
| Builder | Railpack |
| Node.js | 24 |
| Build Command | `npm ci` |
| Pre-deploy Command | `npm run db:prepare` |
| Start Command | `npm start` |
| Healthcheck Path | `/ready` |

حدد إصدار Node.js للبناء عبر متغير الخدمة `RAILPACK_NODE_VERSION=24` إذا لم يحدده إعداد البناء بالفعل.

Railway يحدد متغير `PORT`؛ لا تثبّت منفذًا مختلفًا في خدمة الإنتاج. تجنب استبدال أمر التجهيز بأمر يهيّئ القاعدة من الصفر عند كل تشغيل.

## 3. المتغيرات والقرص الدائم

أضف Volume لخدمة التطبيق عند `/data`. متغير `UPLOAD_PATH=/data/uploads` يجعل الوثائق داخل القرص الدائم؛ تخزينها في نظام ملفات الحاوية وحده لا يضمن بقاءها بعد إعادة النشر. الخادم ينشئ مجلدًا خاصًا ويتحقق من إمكانية الكتابة فيه، ولا يعرضه كمسار تنزيل عام.

| المتغير | القيمة أو طريقة الإعداد |
|---|---|
| `NODE_ENV` | `production` |
| `DATABASE_URL` | مرجع الرابط الخاص بخدمة PostgreSQL، مثل `${{Postgres.DATABASE_URL}}` إذا كان اسم الخدمة `Postgres` |
| `DB_SSL` | `disable` عند استخدام شبكة Railway الخاصة كما في المرجع السابق |
| `JWT_SECRET` | سر عشوائي مستقل لا يقل عن 32 حرفًا |
| `JWT_REFRESH_SECRET` | سر عشوائي آخر مستقل لا يقل عن 32 حرفًا |
| `ALLOWED_ORIGINS` | `capacitor://localhost,https://localhost,http://localhost` مع إضافة نطاق واجهة الويب الفعلي عند استخدامها |
| `TRUST_PROXY` | `1` |
| `UPLOAD_PATH` | `/data/uploads` |
| `MAX_FILE_SIZE` | `5242880`، أي 5 MiB كحد أقصى |

قيمة `DATABASE_URL` يجب أن تبقى مرجعًا خاصًا في إعدادات Railway؛ لا تنسخ الرابط بما يحويه من بيانات اتصال إلى ملفات المصدر. اسم خدمة PostgreSQL في المرجع يجب أن يطابق اسم الخدمة الفعلي.

مصادر Capacitor قيم `Origin` تستخدمها الواجهة داخل التطبيق؛ لا تعني أن قاعدة البيانات أو API تعمل عند `localhost` على الهاتف. أضف نطاق لوحة الإدارة أو واجهة الويب بصيغته الكاملة، مثل `https://example.com`، إلى القائمة إن كانت مستضافة منفصلة. لا تستخدم `*` في الإنتاج.

لتوليد المفتاح الأول محليًا:

```bash
openssl rand -hex 32
```

وللمفتاح الثاني شغّل أمرًا جديدًا مستقلًا:

```bash
openssl rand -hex 32
```

أدخل كل قيمة في متغيرها داخل Railway. ملف `.env.example` يحتوي على أسماء إعدادات وقيم تجريبية وحقول أسرار فارغة؛ ملف `.env` الفعلي مستبعد من Git.

### الاتصال المشفر بقاعدة البيانات

صورة PostgreSQL 18 المعتادة في Railway قد تستخدم شهادة ذاتية التوقيع. الخيار أعلاه يتصل بالخدمة عبر الشبكة الخاصة ويحدد `DB_SSL=disable` صراحة. إذا احتجت إلى اتصال TLS، استخدم `DB_SSL=require` مع شهادة موثوقة عند اللزوم:

```text
DB_SSL=require
DB_SSL_CA_FILE=/path/to/trusted-ca.pem
```

`DB_SSL=require` يفعّل التحقق من الشهادة واسم المضيف. لا يعطّل الخادم التحقق لتجاوز شهادة غير موثوقة. لا تجمع بين `DB_SSL=disable` ورابط يفرض `sslmode=require`؛ الإعدادات المتعارضة مرفوضة. مخطط KNTR لا يتطلب تثبيت PostGIS أو امتدادات PostgreSQL إضافية لهذه المرحلة.

## 4. تجهيز قاعدة البيانات

نفّذ من مجلد الخادم، بعد توفير إعدادات اتصال مناسبة للبيئة:

```bash
npm ci
```

```bash
npm run db:prepare
```

في Railway ينفّذ أمر **Pre-deploy** التجهيز داخل بيئة الخدمة. إذا كانت القاعدة فارغة، ينشئ المخطط ويطبّق الترحيلات. إذا كانت قاعدة KNTR موجودة، يطبق الترحيلات غير المسجلة فقط، ويتحقق من اكتمال الجداول وقيود السلامة. يحتفظ جدول `kntr_schema_migrations` باسم كل ترحيل وبصمته وتوقيت تطبيقه.

خذ نسخة احتياطية قبل ترقية قاعدة تحتوي على بيانات. إن كانت القاعدة غير فارغة ولا تحتوي على مخطط KNTR مكتمل، يتوقف التجهيز بدل حذف المحتوى أو تخمين إصلاحه. وإذا فشل ترحيل، يتراجع عن معاملته ويتوقف؛ تُراجع المشكلة قبل إعادة النشر. لا تعدّل ملف ترحيل سبق تطبيقه؛ أضف ترحيلًا مرقمًا جديدًا عند الحاجة إلى تغيير لاحق.

## 5. إنشاء المدير مرة واحدة

بعد نجاح تجهيز القاعدة، أضف هذه المتغيرات مؤقتًا في بيئة التنفيذ الخاصة:

| المتغير | المطلوب |
|---|---|
| `ADMIN_BOOTSTRAP_EMAIL` | البريد الفعلي للمدير |
| `ADMIN_BOOTSTRAP_PHONE` | 8 إلى 15 رقمًا، مع `+` اختيارية في البداية |
| `ADMIN_BOOTSTRAP_NAME` | اسم المدير |
| `ADMIN_BOOTSTRAP_PASSWORD` | 12 حرفًا على الأقل، تتضمن حرفًا ورقمًا ورمزًا، وبحد أقصى 72 بايت UTF-8 |

شغّل الأمر داخل بيئة يمكنها الوصول إلى قاعدة البيانات الخاصة، مثل جلسة Railway SSH لخدمة التطبيق:

```bash
npm run admin:create
```

لا تستخدم كلمة مرور نموذجية مشتركة. الأمر ينشئ مديرًا جديدًا بكلمة مرور مخزنة كتجزئة؛ إذا كان البريد أو الهاتف موجودًا، يرفض الإنشاء دون ترقية الحساب الموجود أو تغيير بياناته. لا يُشغّل هذا الأمر ضمن `db:prepare` أو تلقائيًا عند كل نشر.

بعد نجاحه، احذف جميع متغيرات `ADMIN_BOOTSTRAP_*` من الخدمة وأعد نشرها لتزول من بيئة العملية العادية. احفظ بيانات الدخول في مدير كلمات مرور خاص.

## 6. الجاهزية وربط الجوال

بعد نجاح النشر، ولّد نطاق HTTPS من إعدادات شبكة خدمة التطبيق. تحقق من:

```text
https://<نطاق-الخادم>/health
https://<نطاق-الخادم>/ready
```

`/health` يثبت استجابة العملية. `/ready` يجب أن يعيد `200` و`status: ok`؛ حالة `503` تعني أن اتصال القاعدة أو المخطط المطلوب غير جاهز. لا تعتبر نجاح `/health` وحده دليلًا على إمكانية تنفيذ الطلبات.

عنوان API الذي يُضبط في واجهتي Android وiOS هو:

```text
https://<نطاق-الخادم>/v1
```

اختبر تسجيل الدخول بحساب عميل وحساب سائق، وطلبًا نقديًا وآخر بالمحفظة، وتحديثات Socket.IO ورفع وثيقة وتنزيلها بصلاحية صاحبها. اختبر بقاء الوثائق بعد إعادة نشر الخدمة. بعد نجاح هذه الاختبارات على الخادم المنشور تبدأ مرحلة بناء Android على جهاز، ثم iOS.

## حدود هذه المرحلة

إعداد الخادم لا يفعّل إشعارات Firebase/APNs ولا التتبع المستمر في الخلفية ولا توقيع تطبيقات المتاجر. لم يُنفّذ هنا بناء APK/AAB أو IPA. نجاح الاختبارات المحلية يُسجل في تقرير المرحلة؛ أما نجاح النشر واختبارات الأجهزة فيتطلب تحققًا مستقلًا بعد إتاحة موارد Railway.
