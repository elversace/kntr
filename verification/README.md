# إعادة تشغيل اختبارات الإصلاح

تشغّل اختبارات API قاعدة PostgreSQL مؤقتة وخادم التطبيق محليًا، وتستخدم بيانات وحسابات اختبار جديدة لكل تشغيل. لا تتصل بقاعدة الإنتاج. راجع ملفات `stepN-results.json` لمعرفة النتائج المسجلة؛ وجود سكربت اختبار وحده لا يعني نجاحه.

## المتطلبات والتثبيت

- Linux بمعمارية x64، وNode.js 18.11 أو أحدث، وnpm.
- مستخدم نظام عادي يملك صلاحية الكتابة في مجلد `verification`. يرفض PostgreSQL التشغيل بحساب `root`. لا يلزم حساب نظام باسم `postgres`؛ الاسم `postgres` داخل الاختبارات هو دور قاعدة البيانات فقط.
- تثبيت تبعيات الخادم وتبعيات الاختبار. الحزمة القابلة للتنزيل لا تتضمن `node_modules` أو ملفات قواعد الاختبار المؤقتة.

من جذر الحزمة:

```sh
cd kntr-package/kntr-backend
npm ci
cd ../../verification
npm ci --foreground-scripts
```

التبعيات المباشرة مثبتة بإصدارات محددة في `package.json`: `pg` بإصدار `8.23.1`، و`socket.io-client` بإصدار `4.8.4`، و`@embedded-postgres/linux-x64` بإصدار `18.4.0-beta.17`. يثبت `npm ci --foreground-scripts` شجرة التبعيات المحددة في `package-lock.json` المرفق دون تحديث الإصدارات. عند تعديل التبعيات عمدًا، يمكن إعادة إنشاء ملف القفل بواسطة `npm install --foreground-scripts`.

حزمة PostgreSQL تضم الملفات التنفيذية والمكتبات. يشغّل `postinstall` الخاص بها ملف `scripts/hydrate-symlinks.js` لإنشاء روابط مكتبات نسبية من الملف المرفق `native/pg-symlinks.json`؛ هذا السكربت لا يحمّل ملفات إضافية. اترك سكربتات التثبيت مفعّلة، لأن تجاوزها بواسطة `--ignore-scripts` قد يترك روابط المكتبات ناقصة.

## التشغيل بالترتيب

```sh
npm run test:step1
npm run test:step2
npm run test:step3
npm run test:step4
```

يشغّل `npm test` المراحل الأربع بالترتيب ويتوقف عند أول فشل. يجب وجود ملف `stepN-tests.cjs` المقابل لكل مرحلة قبل تشغيلها. المراحل تغطي الصلاحيات والتتبع، ثم تأكيد التسليم وQR، ثم المحفظة والمستحقات، ثم رفع مستندات السائق.

كل تشغيل يختار منافذ محلية متاحة وينشئ مجلدًا من نوع `stepN-run-*`. يحتوي المجلد على قاعدة الاختبار وسجلات `initdb.log` و`postgres.log` و`server.log` وملفات الرفع. يوقف السكربت الخادم وقاعدة البيانات عند الانتهاء، ويكتب تقريرًا في `stepN-results.json`. يبقي مجلد التشغيل للمراجعة؛ يمكن حذفه بعد توقف الاختبار إذا لم تعد تحتاج سجلاته. إعادة تشغيل مرحلة تستبدل تقرير نتائجها السابق.

## مسار PostgreSQL وPostGIS

يُستخرج مسار `native` من حزمة PostgreSQL المثبتة بجانب الاختبارات. يعمل ذلك أيضًا مع رابط `node_modules` الموجود في بيئة العمل؛ لا يوجد اعتماد على مسار مطلق لبيئة المراجعة.

يمكن تحديد ملفات تنفيذية أخرى عبر `POSTGRES_NATIVE_PATH`. يجب أن يشير المتغير إلى مجلد `native` نفسه، وفيه `bin/initdb` و`bin/postgres` و`lib`، وأن يكون متوافقًا مع Linux x64. الإصدارات التي استُخدمت للتحقق هي PostgreSQL 18.4؛ استخدام إصدار آخر يحتاج إعادة التحقق:

```sh
POSTGRES_NATIVE_PATH=/absolute/path/to/native npm run test:step1
```

القيمة الافتراضية `SKIP_POSTGIS=1` تحذف سطر إنشاء امتداد PostGIS عند إعداد قاعدة الاختبار، لأن حزمة PostgreSQL المرفقة لا تتضمن هذا الامتداد. هذه الاختبارات **لا تتحقق من PostGIS أو استعلامات البيانات الجغرافية**؛ حساب المسافة الحالي في التطبيق يتم داخل JavaScript. تظهر هذه الحدود في تقارير النتائج.

يمكن استعمال `SKIP_POSTGIS=0` لتحميل مخطط القاعدة كاملًا إذا حددت ملفات PostgreSQL تتضمن PostGIS:

```sh
POSTGRES_NATIVE_PATH=/absolute/path/to/postgis-native SKIP_POSTGIS=0 npm run test:step1
```

اختبار ترحيل البيانات التاريخية في المرحلة 2 ينشئ قاعدة اختبار إضافية ويستبعد PostGIS أيضًا؛ فهو يتحقق من سلامة سجل الدفع والفهرس الفريد، ولا يختبر الوظائف الجغرافية.

## اختبارات الواجهة وحدود التحقق

سكربتا `step2-browser-tests.py` و`step3-browser-tests.py` مستقلان عن اختبارات API ويتطلبان Python وPlaywright وChromium. إصدار Playwright المستخدم هو `1.62.0`. تُنفّذ الأوامر التالية من مجلد `verification`. مثال تثبيت على Debian أو Ubuntu، ثم إعداد بيئة Python منفصلة:

```sh
sudo apt-get install chromium
python3 -m venv .venv-browser
.venv-browser/bin/python -m pip install playwright==1.62.0
.venv-browser/bin/python step2-browser-tests.py
.venv-browser/bin/python step3-browser-tests.py
```

يستخرج سكربت المتصفح مسار المشروع من موقع ملفه، ويبحث عن `chromium` أو `chromium-browser` في `PATH`. يمكن تحديد ملف تنفيذي آخر بواسطة `CHROMIUM_PATH`، دون تعديل السكربت. تُشغَّل ملفات HTML في Chromium مع محاكاة جميع ردود API وحظر الاتصالات الخارجية:

```sh
CHROMIUM_PATH=/absolute/path/to/chromium .venv-browser/bin/python step2-browser-tests.py
```

هذه أدلة على سلوك واجهة HTML فقط. لا تمثل اتصالًا حقيقيًا بالخادم، ولا بناء أو تشغيل تطبيق Android أو iOS على جهاز أو محاكي. نسخ HTML المضمّنة في Android وiOS تُفحص كصفحات متصفح، دون التحقق من إضافات Capacitor أو صلاحيات النظام أو التوقيع أو متاجر التطبيقات.

تُكتب نتائج المحاكاة في `step2-browser-results.json` و`step3-browser-results.json`. تبيّن التقارير صراحة أن ردود API محاكاة، وتحفظ نتائج كل نسخة HTML وأي أخطاء للمتصفح.

## اختبار الربط الفعلي بين الواجهة والخادم

يشغّل `endtoend-tests.cjs` قاعدة PostgreSQL وخادم API محليين ومعزولين بواسطة نفس أدوات الاختبار السابقة، وينشئ حسابي عميل وسائق وحساب إدارة تجريبيين. ثم يشغّل Chromium في سياقين منفصلين للعميل والسائق. يقدم الخادم الفعلي HTML عند `/app`، وتُحظر خطوط الويب الخارجية؛ جميع طلبات HTML وAPI تصل إلى الخادم دون محاكاة. تختبر هذه النسخة كذلك سياسة أمان المحتوى التي تصل مع الصفحة.

بعد تثبيت متطلبات Node وبيئة Playwright أعلاه، شغّل من مجلد `verification`:

```sh
PYTHON_PATH="$PWD/.venv-browser/bin/python" node endtoend-tests.cjs
```

يحدد `PYTHON_PATH` ملف Python التنفيذي الذي ثبتت فيه Playwright. عند حذف المتغير، يستعمل السكربت `python3` من `PATH`. يمكن أيضًا تحديد `CHROMIUM_PATH` اختياريًا؛ عند حذفه، يُبحث عن `chromium` أو `chromium-browser` في `PATH`.

يغطي الاختبار مسارين كاملين: إنشاء طلب نقدي أو بالمحفظة، وقبوله وبدء التوصيل وعرض QR من حساب السائق، ثم تأكيد الاستلام من حساب العميل وتحديث حالة السائق. يتحقق Node من قاعدة البيانات الفعلية: تسليم الطلبين، وسجل دفع واحد بالمبلغ المطابق لكل طلب، وعدم خصم المحفظة للطلب النقدي أو خصمها مرتين للطلب المدفوع بالمحفظة، ومطابقة الرحلات والأرباح وإجمالي إنفاق العميل.

يحفظ `endtoend-browser-results.json` نتائج المتصفح ومساري التسليم وردود API الفعلية. يحفظ `endtoend-results.json` نتائج فحص قاعدة البيانات. تظهر في تقرير المتصفح القيم `actualBackend: true` و`apiMocked: false` و`native: false`. تُحفظ سجلات الخادم والمتصفح وقاعدة الاختبار داخل `endtoend-run-*`، ويُوقف الخادم وقاعدة البيانات بعد الانتهاء. إعادة التشغيل تستبدل تقريري النتائج السابقين.

هذا الاختبار يتحقق من اتصال HTML بالخادم المحلي، ولا يتحقق من نشر الواجهة على أصل مختلف أو تشغيل Android وiOS الأصليين أو مزود دفع خارجي أو انتقال النقد فعليًا. يبقى اختبارا الواجهة في المرحلتين 2 و3 منفصلين، وجميع ردود API فيهما محاكاة.


## تقديم الواجهة والتسجيل والدخول الفعلي

يشغّل الاختبار التالي PostgreSQL وخادم HTTP وChromium معزولة، ويتحقق من `/` و`/app` و`/admin`، ومن عدم تقديم ملفات المستودع أو الأسرار أو الرفع. يستخدم المتصفح استمارة التسجيل لإنشاء عميل وسائق جديدين، ثم يسجل خروجهما ودخولهما ويختبر كلمة مرور خاطئة. يدخل المدير بلوحته ويخرج منها، ثم تُختبر صلاحية التوكن الملغى على الخادم. لا توجد محاكاة HTML أو API؛ تُحظر خطوط الويب الخارجية فقط.

```sh
npm run test:hosted-auth
```

يستخدم نفس متطلبات Node وPython وChromium المذكورة أعلاه، ويمكن تحديد `PYTHON_PATH` و`CHROMIUM_PATH`. النتائج في `hosted-auth-results.json` و`hosted-auth-browser-results.json`. الحسابات والرصيد التجريبي في قاعدة محلية معزولة فقط؛ ليست حسابات في Codespaces، ولا يثبت هذا بناء Android أو iOS. تستعمل فحوص المتصفح دوال JavaScript كشرط انتظار لتعمل مع سياسة CSP دون السماح بـ`unsafe-eval`.

## تهيئة خادم الاختبار

النسخة المعدّة للاستضافة تتضمن بوابة مستقلة لإعدادات الإنتاج والقاعدة وCORS والجاهزية:

```sh
npm run test:startup
```

تُكتب النتيجة في `startup-results.json`. اختبارات هذه المرحلة تستخدم PostgreSQL وHTTP وWebSocket فعلية محليًا. اختبار TLS يتحقق من خيارات الشهادة ورفض الإعدادات المتعارضة فقط؛ لا ينشئ اتصال PostgreSQL مشفرًا. المخطط الحالي يستخدم UUID المدمج ولا يطلب امتداد PostGIS أو pgcrypto، ولا توجد شهادة تشغيل على Railway قبل النشر. تعليمات PostGIS السابقة تصف آلية الاختبار التاريخية عند وجوده في مخطط قديم.
